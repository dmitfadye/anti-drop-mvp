# Рекомендуемый стек и архитектуры

**Сохранить Python/FastAPI и объяснимые правила.** Крупная миграция сейчас отнимет время у проверки ценности. Дата 08.10.2026; фактические версии и ограничения проверки см. [реестр](EVIDENCE_REGISTER.md). Оценки времени ниже — допущения для небольшой команды, не оферта.

## Альтернативы и стоимость выбора

| Альтернатива | Когда уместна | Решение сейчас |
|---|---|---|
| React + TypeScript + Vite | Несколько команд/сложные состояния, библиотека банка, много экранов | Вернуться после контракта банковского UI; перенос трёх экранов оценочно 4–7 дней + regression. Сейчас выигрыша для демонстрации не доказано |
| Vue + TypeScript | Те же задачи, если команда уже владеет Vue | Аналогичный выбор по компетенциям; не мигрировать ради предпочтений аудитора |
| Next.js | SSR/SEO, маршрутизация публичного сайта | Для банковского интерактивного экрана SEO не нужно; серверный слой усложнит deployment |
| Java / Spring Boot | Банк требует JVM и располагает командой сопровождения | Python adapter оставить для пилота, согласовать контракт. Полный перенос/повторная валидация оценочно 10–20 дней, выгода сейчас отсутствует |
| Go | Строгие latency/RSS и измеренный bottleneck | Не доказано. Цена переписывания/регрессии оценочно 8–15 дней |
| Node.js / NestJS | Единая TS-команда с реальной компетенцией | Не уменьшает продуктовые пробелы; 7–12 дней на перенос без доказанного выигрыша |
| Redis | Shared TTL/rate limiting/cache между репликами | Не использовать как основной аудит/ledger; добавить при реальной потребности и согласовать лицензию версии |
| ClickHouse | Большой поток аналитики с профильными запросами | Для двух CSV не нужен; хранить минимум событий, экспортировать в банковскую аналитическую платформу |
| PostgreSQL + pgvector / Qdrant / OpenSearch | Векторный retrieval / полнотекстовый поиск | Задачи retrieval нет: не добавлять |
| Celery/RabbitMQ | Долгие jobs и подтверждённая потребность в retry/очереди | Возможно позже для расследования/локализации контента, не для короткого rules engine |
| Kafka | Уже существующий банковский event backbone | Подключить адаптер к имеющемуся контуру; не разворачивать новый кластер для MVP |
| Kubernetes | Банк предоставляет platform и стандартизированный путь | Не делать отдельную платформу силами команды 2–5 человек |
| Loki/OTel/Prometheus/Grafana | Интеграция в эксплуатацию | Использовать существующие банковские средства; не настраивать всё одновременно |

Неустановленные альтернативы не проходили benchmark и лицензирование; цифры времени — порядок стоимости, сильно зависящий от команды. Подробное сравнение версии каждой отвергнутой технологии нецелесообразно, поскольку она не входит в целевой scope.

## Три архитектуры

**Быстрый надёжный MVP:** один FastAPI, локальный HTML/CSS/JS, детерминированные fixtures, валидированные snapshots одного клиента, один case mock с устойчивым состоянием и явной пометкой sandbox; sqlite допустим только для автономной демо-фиксации с ограничением одного процесса, предпочтительнее сразу согласованный PostgreSQL если команда его знает. Без SIM, денежных наград и автономного ограничения переводов. Демо запускается без сети и проходит негативные сценарии.

**Банковский пилот:** gateway/SSO → FastAPI → rules/templates; доверенный read-only event adapter, PostgreSQL для минимального case/audit и event dedup, bank case adapter с отдельной identity, локальные ассеты, закрытый runtime egress, redacted observability. Shadow scoring сначала, затем согласованный UX-эксперимент; решение о платеже остаётся у банка. DB schema version, backup и restore проверяются.

**Масштабируемая цель:** API/UX и обработчики событий отделяются только при измеренном давлении на latency/throughput; partition by subject, оконное состояние, event dedup, versioned rules, outbox/retry для действий, деградация к банковскому стандартному предупреждению. Реплики/HA по согласованным RTO/RPO; данные и analytics интегрируются с платформой банка. Kafka/Kubernetes используют существующий сервис, а не строятся заново.

## AI evaluation без добавления лишнего ИИ

LLM не нужен для определения риска по нынешним правилам; генерация юридических предупреждений увеличит вариативность и review burden. Предварительно переведённые/согласованные шаблоны надёжнее. RAG не решает нынешнюю задачу. Возможное классическое ML: ranking риска после появления достаточной разметки и baseline; внедрять только при out-of-time улучшении recall при фиксированном FPR.

Фреймворк качества применим уже к правилам: независимые эпизоды norm/attack/ambiguous, семейные сборы, зарплата+наличные, повтор событий, разные зоны, границы суммы/окна, SIM=0, новый device, пустые/неполные данные. Эталон — решение профильного аналитика с adjudication спорных случаев; два CSV не являются validation set. Train/tune/test разделить по пользователю и времени; считать episode-level precision/recall/FPR, PR curve и alert rate, p95 latency и CPU cost/request. Никаких промптов/галлюцинаций в текущем коде нет; применимы input validation и безопасность шаблонов. При неопределённости — «нужна проверка», не обвинение/блокировка. Рекомендуемые критерии обсуждения: FPR ≤1% на независимо размеченных нормальных эпизодах, recall ≥70% на известных типах риска, p95 ≤200 ms для согласованного batch/железа; значения являются гипотезами для gate, не измеренными достижениями. На небольшой тестовой выборке указывать интервалы неопределённости.
